## P2 — `handleSetMonthsSincePeriod`'s date math can silently roll into the wrong month on day-29/30/31 calls

- **File:** `app/dev-panel.tsx:254-256`
  ```ts
  const d = new Date()
  d.setMonth(d.getMonth() - months)
  const iso = toDateStr(d)
  ```
- **Issue:** `Date.setMonth` doesn't clamp to the target month's last day — it overflows into the *next* month when the current day-of-month doesn't exist there. E.g. on July 31st, tapping "1mo" computes `new Date(2026, 5, 31)` → June has only 30 days → JS normalizes this to **July 1st**, i.e. 0 months ago, not 1. The same failure applies to any of the `[3, 6, 12, 14]` buttons whenever `today.getDate()` exceeds the target month's day count — which happens on the 29th–31st of Jan/Mar/May/Jul/Aug/Oct/Dec for various offsets.
- **Why this matters here specifically:** the whole point of this scrubber is to exercise `shouldOfferMenopauseUpdate`'s `>= 12` months threshold (`lib/menopauseStage.ts:22-30`) precisely at the boundary (the "14" button is clearly there to test *past* the 12-month cutoff). A silent one-month rollover on the wrong calendar day could make the "12" button fail to cross the threshold, or make "14" land back at 13 — undermining the one thing this tool exists to test.
- **Not a novel pattern:** the identical `setMonth(getMonth() ± N)` idiom (with the same overflow behavior) already exists at `app/onboarding/pregnancy/index.tsx:398`, so this isn't a regression introduced uniquely by U10 — it's a pre-existing gap in the codebase's date-math conventions that this new caller inherited. No `addMonths`-style safe helper exists anywhere in the repo to reach for instead.
- **Impact:** Low probability (only reproduces on ~7 specific calendar days/year, and only for some of the four button values on those days), dev-only surface, and it's self-correcting the next time someone taps a different button. Not fixed here (report only).

## P2 — New stage/months `Pressable` buttons don't disable while `busy`, unlike the sibling `ActionRow`

- **File:** `app/dev-panel.tsx:436-465`
- **Issue:** `ActionRow` (used for "Seed menopause data" and "Menopause onboarding") disables itself via `disabled={!!busy}` while any `run()` call is in flight (`app/dev-panel.tsx:814`). The new raw `Pressable` stage buttons (Peri/Meno/Post) and months buttons (3/6/12/14) — both introduced by this commit — have no equivalent guard, so a user can fire a second `handleSetMenopauseStage`/`handleSetMonthsSincePeriod` call while one is still awaiting its `supabase.auth.getSession()` + upsert round-trip.
- **Impact:** Low — `run()` itself has no re-entrancy lock either (pre-existing, shared by every handler in this file), so this is consistent with the rest of the panel's handlers, not a regression specific to this feature. Worst case is two overlapping best-effort `profiles` upserts, both idempotent no-ops on the same row. Purely a minor UX/robustness inconsistency within the same file (`ActionRow` guards, these two new button groups don't). Not fixed here (report only).

## P2 — Seeded `period` rows never produce `'heavy'`, one of the three real flow-level values

- **File:** `lib/devSeed.ts:260-264`
  ```ts
  value: randFrom(['light', 'medium'] as const),
  ```
- **Issue:** The real period-logging form (`components/menopause/MenopauseLogForms.tsx:165-170`) defines `type Flow = 'light' | 'medium' | 'heavy'` with all three offered to the user. The seed only ever samples `'light'` or `'medium'`, so `'heavy'` is never exercised by seeded data. This doesn't break anything — `MenopauseTimeline.entrySubtitle` (`components/menopause/MenopauseTimeline.tsx:65`) just does `capitalize(row.value)` on whatever string is present — it's purely a coverage gap in the seed's realism, not a shape mismatch. Not fixed here (report only).
